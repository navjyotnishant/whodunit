# Changelog

All notable changes to whodunit are documented in this file.

The format is based on [Keep a Changelog](https://keepachangelog.com/en/1.1.0/),
and this project adheres to [Semantic Versioning](https://semver.org/spec/v2.0.0.html).

## [Unreleased]

### Fixed

- Codex MCP calls were undercounted by 44%. Codex tags an MCP call one of two ways — a prefixed name (`mcp__linear__save_comment`) or a bare name with the server in a separate `namespace` field — and only the first was counted; the `namespace` field was not read at all. Measured on one machine, 311 calls used the counted form and 243 used the ignored one. MCP tool names are now qualified as `server__tool`, so a server's `save_comment` no longer merges with a local tool of the same name. A namespace alone does not imply MCP: Codex also uses it for built-ins such as `multi_agent_v1`, which are correctly not counted.
- Antigravity (`agy`) acceptance rate was structurally unmeasurable. Every entry was written with outcome `unknown`, and the adapter's own comment stated that agy records no rejection signal — it does. `steps.status` is `NOT NULL`, indexed, and populated on every row. The eight non-success rows on this machine resolve into three distinct meanings rather than one: six carry `error_details` beginning "Permission denied" (a human declining, which is exactly what an acceptance rate is measured against), one "context cancelled", one nothing at all. An unrecognised status still maps to `unknown` rather than being folded into `failed`, because a status this code has not seen is a gap in what we know, not evidence of an error.

### Changed

- `make check` is now the single entrypoint for every gate — formatting, vet, tests, race detector, performance budgets, benchmark smoke-check, and the dashboard export check. CI calls these targets rather than keeping its own copy of each command, so the checks a developer runs and the checks CI runs cannot drift apart.
- Performance budgets extended from 3 gates to 13, covering both adapters that were previously unguarded. They assert and fail rather than printing a number, and scaling tests take the best of five runs on each side — a single timing on a shared runner is mostly noise.
- A test that asserts on elapsed time but is not selected by `make perf` now fails the build. The performance gate selects tests by name, so a badly-named timing test does not report as skipped, it simply never runs — which had already happened to two new tests before this check was added.

## [0.2.0] - 2026-08-14

### Added

- `dun verify` — one command that checks whether attribution is actually working: install, agents, hooks, journal, sync, and every registered repository, each finding paired with the command that fixes it. Output is grouped into sections with status icons, and the exit code is non-zero only for genuine breakage, so it can gate CI without failing a deliberate local-only setup.
- `dun sync` publishes attribution data to a shared DevLake database, with `dun config datalake` walking through host, database, user and credentials and testing the connection before saving. Publishing then happens automatically on push; the push hook never blocks a push and retries on the next one.
- `dun status` now works outside a git repository, printing a one-line summary of every instrumented repository, and takes `--repo <path|id>` to report on a specific repository from anywhere.
- `dun journal show` and `dun journal purge` take `--repo <path|id>` to inspect or clear another repository's data; purge names the repository before deleting.
- `dun delta` compares velocity and revert rate two ways — assisted vs. undetermined commits in the same window, and a baseline window vs. a recent one — flagging thin data, mismatched windows, and a missing baseline rather than printing a number that looks solid.
- `dun baseline capture` records a dated, immutable pre-adoption snapshot (commit volume, median diff size, revert rate, cadence, purpose mix) so a later before/after comparison has something to compare against.
- `dun init --repo` instruments a repository without changing directory, and a registry records what was instrumented: `dun repos list`, `dun repos candidates` (repositories with agent activity but no hooks), and `dun repos remove`.
- `dun update` upgrades the binary and rewrites hooks everywhere in one step; `dun repos update` rewrites hooks in every registered repository, preserving hooks whodunit did not write. Hooks now record the version that wrote them, so `dun verify` can report stale ones.
- Codex CLI and Antigravity CLI (`agy`) adapters, both reaching `intersected` confidence, alongside Claude Code.
- Transcript locations are configurable per agent via `dun config set agent.<name>.path` or `WHODUNIT_<AGENT>_PATH`, and `dun init` reports which agents it found while you are still watching.
- `dun report` gains inline SVG charts, journal-derived data (acceptance outcomes, per-tool and per-file activity, session engagement), and three presets — `exec`, `adoption`, `detail`. The report stays a single self-contained file with no external requests.
- Commits are classified by purpose (feature, fix, test, docs…) from Conventional Commits type, path heuristics and diff shape, and shown in the report as a distribution plus a commit-by-commit table.
- The DevLake datalake installs from two curl-pipeable scripts — `setup-datalake.sh` brings up the stack and creates the Grafana datasource, `import-dashboards.sh` imports the dashboards into any Grafana. They are separate because the stack is built once while dashboards are re-imported on every release, and neither needs `dun` installed: the database is shared infrastructure, often set up by someone who never runs the CLI. DevLake's compose file is no longer vendored, only fetched from the upstream release asset. DevLake's own Grafana never creates its datasource — its entrypoint authenticates with a password its compose file never sets, so every attempt returns 401 — which is why the setup script creates it.
- `dun config` with no subcommand lists every setting, its value, and whether that value was set or defaulted, because a default and a deliberate choice read identically as a bare number. `dun config set` accepts `monthly_spend`, `backup_days` and `retention_days` alongside agent paths; all three were previously config-file-only, and the report advised a command that rejected the key. The accepted settings, the "unknown setting" message and the help text now read from one table, so they cannot drift apart again.
- The journal keeps daily rotating backups: a compressed copy taken on push, at most once a day, seven generations retained, written before pruning so the week of history predates whatever retention removes. The live database is never touched, and pruning runs only after a successful sync, so anything removed already exists in a second place.
- The hook log keeps five rotated generations of a megabyte each rather than one, holding months of history — long enough to answer "when did this start failing", which is the question the log exists for. `dun ingest` and `dun sync` now record their outcomes and failures there: an unopenable target, an unreachable one, a failed schema check, a failed write. Previously they printed to the terminal and left nothing behind, and `dun ingest` passed an empty error callback, so a transcript that could not be parsed was discarded silently by the code that would have reported it. The sync target is redacted before it reaches the log.
- Bare `dun` opens with a wordmark, the running version, and the full command list. The version is load-bearing rather than decorative: hook staleness is computed from it. The command list is derived from the command tree instead of a hand-maintained array, which had drifted to eight entries while `--help` showed eighteen, leaving `baseline`, `check`, `config`, `daemon`, `delta`, `ingest`, `update` and `version` invisible to anyone who never thought to ask for help.
- Grafana dashboards for the synced data — adoption, executive summary, and a coverage overview — including an export variant any Grafana can import, shipped as a tarball on each release.
- Bare `dun` prints a welcome screen explaining what the tool is, whether the current repository is instrumented, and the next command to run; output across commands is color-coded, honoring `NO_COLOR`, non-TTY output, `TERM=dumb`, and CI.
- Confidence levels explain themselves wherever they appear — `dun status`, the cross-repo listing, and the HTML report — with each method's position on the ladder stated (`intersected` strongest, `observed` weaker because the agent's text was changed before committing).
- Tool calls are classified as accepted, rejected, failed, or unknown, and acceptance rates always display next to the denominator they came from.

### Changed

- The commit hook looks back 30 days rather than 7. Seven covered a working week and lost anything that sat over a holiday or on a long-running branch, which is the work most likely to be agent-heavy; the wider window costs about 26ms per commit against a two-second budget. Retention is derived from that window rather than being a second 30 typed in a package that cannot import the first, because pruning inside the window the hook queries deletes evidence a commit was about to match — silently turning an `intersected` commit into an `observed` one. A `retention_days` below the lookback is refused by `dun config set` and clamped on read, so a value written before the minimum existed cannot route around the guarantee.
- `dun status` reports the real unsynced backlog — what has been recorded since the target last heard from this repository — rather than counting every journal entry ever recorded. A repository that had just published still claimed 2,726 events outstanding, which does not merely overstate the number: it says publishing accomplished nothing. What a sync transmits is reported separately, because a sync genuinely does retransmit the full history each time. The remote lookup is a single indexed read, and the cross-repo view answers for every repository in one query rather than one connection and one two-second timeout each.
- `dun sync` reports progress. It was silent between announcing the payload and reporting the result, which on 16,890 rows reads as a hang; it now names each network step and draws a progress bar through the write, to a terminal only, since a carriage-return redraw into a CI log produces thousands of lines.
- The local-only warning argues from correlation rather than data loss. The journal is regenerable from the agents' own transcripts, so "you will lose your data" overstates the case; what publishing buys is joining attribution to what happened next. What genuinely does not come back is a pre-adoption baseline and any commit whose agent transcript has since been pruned, and the message names those two rather than making a blanket claim.
- Status glyphs are text rather than emoji. Emoji carry their colour from the font, so a checkmark stayed green under `NO_COLOR` — the one case where output is meant to be plain — and rendered double-width, misaligning every column after the marker.
- **Breaking:** the `session` trailer value is now a repo-scoped hash rather than the agent's raw session id, which on Claude Code doubled as the transcript filename. Existing commits keep their original value; new commits are no longer a pointer into local transcript files and cannot be correlated across repositories.
- **Breaking:** the journal moved from one SQLite file per repository under `.git/dun/` to a single database under `~/.whodunit`, keyed by repository root-commit SHA. Baseline snapshots moved to `~/.whodunit/baselines/` so they survive a fresh clone or `git clean -xfd`.
- `~/.whodunit` separates settings (`config.json`) from regenerable data (`data/journal.db`) and non-regenerable baselines.
- `ratio` is a real measurement instead of a hardcoded `1.00` — the agent's deduplicated share of a commit over total changed lines. It is omitted rather than reported as `0.00` when there is no line-level evidence, and shares below 0.005 are omitted rather than rounded to zero.
- Attribution matches line by line, file-scoped, instead of whole tool outputs against whole diff hunks, so an agent's write still matches on the lines a developer kept. Only hashes are stored, never the lines themselves.
- The commit hook writes the journal itself, so a normal install reaches `intersected` without anyone remembering to run `dun ingest`.
- Repository identity, contributor email (from `git config user.email`, captured at `dun init`) and per-repository metadata are recorded once per repository rather than on every row, and `dun journal purge` removes them too.
- `dun report` writes to the system temp directory by default and prints an absolute `file://` URL.
- Repeat `dun ingest` runs are roughly 7× cheaper on unchanged transcripts, and the commit hook stays well inside a 2-second budget.
- DevLake dashboards are imported rather than mounted, so the bundled compose file stays stock and dashboards remain editable in Grafana.

### Fixed

- Attribution silently produced nothing on Windows. Four independent causes, each sufficient on its own: the directory-name encoding kept the drive colon and produced a name Windows refuses to create; the session directory came from an unresolved path, so the slug named a directory that exists nowhere and no transcript was ever found; line hashes included the raw path, so the staged half (`C:\repo\main.go`, from git) and the recorded half (`C:/repo/main.go`, from agents that are Node programs) never agreed; and staged files were matched against journal entries by exact string, so no key ever matched. Every one failed the same way — no error, no sessions found, every commit stamped `undetermined`, which reads as "no AI was used" rather than "the two halves spelled the path differently". Paths are now resolved once per file through a single implementation, and matching tolerates a volume prefix on one side while keeping `C:/repo` and `D:/repo` distinct: folding aggressively enough to merge them would manufacture attribution that never happened. The sync password was also unprotected there — `os.Chmod` only toggles the read-only attribute and `os.Stat` synthesises the mode it returns, so writing `0600` granted nothing and checking for it read back a number the runtime invented. The key and ciphertext now carry a protected owner-only ACL, verified by reading the descriptor back.
- A commit made while the daemon was ingesting lost its attribution. One journal file per machine is written by the commit hook on every commit, the daemon every five seconds, and `dun ingest` by hand, across every repository at once — and the database was opened with no `busy_timeout` under SQLite's default rollback journal, so a second writer failed immediately with `SQLITE_BUSY`. Every caller treats a journal error as "record nothing and carry on", which is correct and made the cost invisible: the commit was stamped `undetermined`. Reproduced at 3 failures in 200 concurrent writes before the fix, none after, with WAL, a five-second busy timeout, and a retry around schema creation that `busy_timeout` cannot cover because there is no database file to wait on yet.
- Backups were disabled on every fresh install. The `backup_days` default was applied after the "no config file" early return, so a machine with no `config.json` loaded zero, which `journal.Backup` reads as "explicitly disabled" — it silently took nothing while the prune beside it still deleted line hashes. The ordering that makes pruning safe, copy first then delete, was absent on exactly the machines most likely to need it: every one, on day one. That also exposed the second half: `backup_days` carried `omitempty`, so `dun config set backup_days 0` wrote no key and read back as the default, meaning the documented way to disable backups quietly re-enabled them.
- `dun config` printed the sync password. The redaction helper returned the raw DSN when the URL failed to parse — precisely when someone is looking at the output, since an unparseable DSN is what they are trying to diagnose — and never touched a password passed as a query parameter. Three of five cases leaked.
- A malformed `config.json` was swallowed. Falling back to the built-in defaults is correct, since a broken file must not silence an agent outright, but nothing reported it on the path that matters: the commit hook never loads the config directly. A stray comma discarded every configured agent path, every commit was stamped `undetermined`, and the only signal was attribution quietly stopping. The hook now logs the parse failure.
- The repositories registry could be read mid-write and fail to parse, taking every cross-repo command down with it — 7 of 100 reads with one concurrent writer, because the write truncated the file before rewriting it. That file is not regenerable: it is the list of repositories someone chose to instrument, and rebuilding it means re-running `dun init` in each one, if they realise that is what happened. It is now written to a temporary file and renamed over the target. On Windows, where a rename is refused while another process holds the file open for reading — exactly the case this protects — the rename retries for about a second rather than failing `dun init` because someone ran `dun status` at the same moment.
- Three user-facing messages said "the last 7 days" long after the window became 30. The behaviour was right and the explanation was wrong, which is worse than either alone: someone debugging a missing trailer reads that their three-week-old session is out of window, believes it, and stops looking. All three derive from the lookback constant now, and a test fails if a literal creeps back.
- Storing the sync password failed with "cannot determine a machine identifier" on machines that plainly have one. The machine id shelled out to a bare command name, which a hook running with a minimal `PATH` need not find; it tries the absolute path first now.
- A fresh DevLake install ended up with a running stack and an empty Grafana. The setup script polled Grafana's health endpoint, which returns 200 well before the API accepts an authenticated write, and DevLake's entrypoint deletes and recreates any datasource named `mysql` seconds after Grafana starts, removing one that landed first. Re-importing dashboards also duplicated them — the export blanked each dashboard's uid, so Grafana minted a random one per import and `overwrite` matched nothing, turning six dashboards into twelve on one re-run. The exports additionally carried the author's own team id, timezone and spend as pinned values, which made valid SQL return nothing on anyone else's machine, in the way that reads as "no data" rather than "not configured".
- A test-only panic path shipped in every release binary: `dun hook panic-probe` triggered a deliberate panic, recovered and harmless, but a test fixture has no business in a shipped binary.
- Commands run outside a git repository say what is wrong and how to proceed (`use --repo <path>`) instead of surfacing `exit status 128`.
- `dun verify` no longer reports per-repository agent session counts when run outside a repository, and distinguishes an agent that is not installed from one whose configured path is wrong.
- `dun delta` counted every assisted commit as undetermined when the trailer sat at the end of a multi-line commit body.
- Release builds report their version instead of reporting none.
- Journal directories are created `0700` and the database `0600`, and existing over-permissive files are repaired on open — the journal records which files were edited and when, and was previously world-readable.
- The schema applies cleanly to MySQL as well as SQLite, fixing three portability bugs (a `TEXT` default, index creation syntax, and an over-long primary key) that made a live deployment impossible.
- `dun check` in CI no longer fails on GitHub's synthetic merge commit, which was never authored through the hooks.

### Security

- The sync password is encrypted at rest with AES-256-GCM under a machine-derived key, replacing environment-variable-only storage that pushed users toward a plaintext credential in `~/.zshrc`. It protects the credential if the file leaves the machine — a backup, a synced dotfiles repo, a copied home directory — but not against a process already running as your user. `dun verify` reports where the password lives and fails when either file is readable by others.
