## [Unreleased]

## [0.6.1] - 2026-09-09

### Added

- **Files an agent writes through a shell command are now attributed.** An agent editing through `Edit`/`Write` was recorded with a file; the same edit made with `cat > main.go <<'EOF'` was recorded as a bare tool call with no file, so it was invisible to attribution and the commit resolved `unmatched` — or `unassisted`, a positive claim that no AI was involved. On one machine's journal that was 7,263 Bash records against 894 Edit/Write ones. The command is now read for the files it *writes* and only for those: a write operator has to name a target, so `ls -l x.go` and `mkdir -p build` still record nothing, while `cat > f <<'EOF' … && git add -A` records `f`. The heredoc body never reaches the journal — a path is a name, the bytes after `<<'EOF'` are file content — and that is asserted by test through the real parse path. No line counts and no hunk hash are recorded, because the command carries no diff and a fabricated one would let a shell edit claim `intersected` on evidence that does not exist; a command that also writes somewhere it cannot name is marked `partial` so an incomplete file set never reads as a complete one. Measured across 21,229 real Bash calls in five repositories: 96.1% of writing commands name a target this extracts. Two known limits: the rule set is per-ecosystem (`gofmt -w` is 8.5% of writes in a Go repo and 0% in a Python one), and PowerShell's `Out-File`/`Set-Content` are not recognised (WHO-238).

### Fixed

- **Agent transcripts were invisible in any repository whose path contained a dot, an underscore, or a space, and their commits were stamped as written by a human.** Claude Code names its transcript directory by replacing every non-alphanumeric character in the working directory with a dash; whodunit replaced only the path separators and dropped the colon, so `~/.orion/projects/x/repo` was sought at `-Users-me-.orion-…` while the client had written `-Users-me--orion-…`. The two names never met. Measured on one machine: 91 git repositories, 14 found under the old encoding and 72 under the corrected one, with 156 transcript directories sitting unread. The colon is now mapped rather than dropped, matching the client — keeping `C:\repo` distinct from `C-\repo` was deliberate, but a slug that is unique and wrong finds nothing at all. `dun repos candidates` decodes the wider encoding by searching which reading exists on disk. A slug over 200 characters is now truncated and suffixed with a base36 hash of the full path, exactly as the client does, so deep worktree paths are found too — the hash was identified by experiment rather than assumption: a directory was created with a 241-character slug, Claude Code was run in it, and the name it wrote was matched (WHO-237).

- **`unassisted` is no longer stamped when the tooling never looked anywhere real.** `unassisted` asserts that no AI was involved, and that claim was reached whenever no transcript was found — including when the directory searched did not exist, because an absent directory and a present-but-empty one both yield no files and no error. With the encoding bug above, commits an agent wrote end to end were recorded as human work. A commit now falls back to `undetermined` — "could not tell", not "nobody did" — when no agent's per-repository transcript directory exists and none produced a session, and the hook log says so and points at `dun verify`. A directory that exists and is empty is still real evidence and still yields `unassisted` (WHO-236, NAV-21). This also changes behaviour for agents that keep one global transcript store rather than a per-repository one — Antigravity and Codex — where a repository the agent was never run in now reports `undetermined` instead of `unassisted`: the store existing says the agent is installed, not that this repository was examined.

- **Note on commits already stamped.** Upgrading fixes what is written from now on; it does not rewrite trailers already in your history. A commit stamped `unassisted` by an affected version stays that way, and the honest reading of one is "this may not have been measured" rather than "no agent was involved". The journal is unaffected — it recorded the agent activity all along — so `dun sync` republishes the corrected picture to a datalake without touching git history.

- Homebrew and Scoop were not updated by the automatic release. `release.yml` runs as a workflow called from `tag-on-prd.yml`, and a called workflow sees none of the caller's secrets unless the caller passes them, so `publish-packages` found `PACKAGING_TOKEN` unset, warned, and reported success. v0.5.0 and v0.6.0 both shipped with the tap and the bucket still at 0.4.0. The caller now passes `secrets: inherit`; 0.6.0 was published to both by hand with the repo's own scripts.

## [0.6.0] - 2026-09-07

### Added

- **The `teams` map in `config.json` now reaches the dashboards.** `dun sync` publishes it to `whodunit_teams`, one row per person keyed on the canonical address, and every team join reads that table first with DevLake's own `teams`/`team_users` as the fallback: a team someone typed on purpose beats one that arrived on a connector sync, and a person in neither source is `(unassigned)`, never dropped. The 0.5.0 notes described this precedence as if it existed; the map was defined and validated and nothing published or read it, so every team panel on a real install showed `(unassigned)`. Publishing replaces the table rather than upserting into it — config is the source of truth for who is on which team, and an upsert would leave someone removed from the map under a stale team forever — while a machine with no teams map leaves the table alone, so it cannot erase what another one published. A person listed under two teams takes the alphabetically first, the same one on every sync. Both routes are documented: the config map, and DevLake's org-plugin CSVs for teams that live there (WHO-211, completing WHO-157).

### Fixed

- The Investment Case and the rebuilt Cost dashboard errored on a fresh datalake with "table whodunit_model_prices doesn't exist" until someone ran `fetch-model-prices.py`. The sidecar schema now creates the table empty, so those panels run before any prices are fetched and report every session as unpriced, which is the truthful state; the fetcher fills it. Nine tables, every one prefixed.

## [0.5.0] - 2026-09-07

### Added

- Linux packages. Every release now carries a `.deb` and an `.rpm` for
  amd64 and arm64 beside the existing archives, so an Ubuntu or Fedora user
  installs with `sudo dpkg -i` or `sudo rpm -i` and nothing else. The
  package depends on `git` and installs only `/usr/bin/dun`; hooks and
  config stay per-repository and per-user as before.
- **A Team Adoption dashboard (`whodunit-teams-board`), answering whether adoption is even across teams or carried by one.** Nothing in the seven existing dashboards could say, and team ownership was the highest-value unsolved question in the category. Every panel groups by team: adoption rate, evidence strength, agent mix, work mix, adoption over time, share of AI-assisted commits, and per-person adoption drawn as a distribution under each team rather than a league table, because a dashboard that opens on named developers ranked by AI use is the objection that ends adoption inside a company. Four panels cross team against the session grain to say how each team uses the tooling, not just how much: session shape (chat, working, agentic, separated by tool-call count), model, permission mode and reasoning effort. The model panel covers only agents that report one and the effort panel covers Codex alone, stated in the tooltips as a subset by design rather than filled in. The rollout questions a manager asks next are on the same page: adoption band per team per week as one state-timeline strip, blank where a week has under 3 commits; weeks from a team's first assisted commit to the first week its share reached half, showing "not yet" in grey rather than a number for a team that has not crossed; lowest, average and highest member inside each team, because a wide spread and a low average are different problems the average alone cannot tell apart; a not-started list of everyone with commits in range and none assisted, which says who and not why, since a repository without the tool and work done by hand on purpose look identical here; acceptance and rework per team, adoption against acceptance as a scatter, and assisted share by team and work type as a heat grid with cells under 5 commits withheld. Ownership by service remains unanswerable and the dashboard does not pretend otherwise: every team touches every repository in the data it was built against, so a repo-to-team mapping would be invented rather than derived.
- **An MCP & Tools dashboard (`whodunit-mcp-board`), reading which integrations the agents actually call, and how widely against how deeply.** The data was already collected and nothing read it: 6,752 MCP calls across 33,303 events on the real lake, 13 server names, 141 distinct tools. Server names are normalised at read time, and that is what makes the page truthful: the same server arrives under several names depending on the transport that invoked it, Linear five ways and Playwright three, so unnormalised the second most-used integration looked like five minor ones. Read time rather than collection time for the same reason as the identity map, so a wrong rule is fixed by editing one expression instead of re-syncing history. Breadth and depth are the organising idea: a server with two heavy users and one with nine light users are identical as a call count and opposite as a rollout decision, so a scatter puts people-using-it against calls-per-person, and a profile table carries first used, people, teams, calls and calls per session. Calls per server per week as a heatmap, where a row that brightens is an integration being picked up and one that fades is being abandoned; team against server as a share grid; a list of people with tool calls and none to an MCP server, who use the agent but not its integrations; and MCP against built-in tools over time as a 100% stack. MCP calls carry no outcome, so there is no per-server failure rate, and the page says so rather than faking one.
- **A Productivity dashboard (`whodunit-productivity`) that reports Output/Effort under five definitions rather than one.** Productivity gain is a ratio and teams disagree about both terms; the previous answer was to show no number at all, which looks like rigour and hides the disagreement. The five definitions of effort now sit side by side as bars from a zero line so a reader takes the row matching how their team counts, and on the demo data they disagree in sign, which is the finding a single headline would have concealed. Effort denominators only: per-person ratios were drafted and cut because they read +137% against per-person-day's +3%, assisted contributors having been active 14.8 days against 6.4, which is more time spent reported as more output per unit of time, the exact error the page exists to prevent. The row moved out of AI Impact on Delivery, which asks whether DORA metrics moved, into its own page with a header stating the framing: no single number exists, every figure is a difference and not a gain because the cohorts are self-selected, and the rework rate is read before any output figure and is a fix rate, not a defect rate. No-evidence commits are excluded rather than counted as unassisted: 715 of 1,546 commits carry one of the four no-evidence statuses, so the comparison names all six statuses and maps those four to NULL in the open, because counting absence as a measured negative is the one error this project treats as cardinal. Every cell carries its n and blanks below 5 per side.
- **The same ratio conditioned on work type and complexity, beside the pooled figure, and a within-person comparison.** When the two disagree, the pooled figure was measuring which work each cohort happened to pick up, not how productive it was, and people reach for an agent on the easier task, so this is the Simpson's-paradox check readable in two seconds: a colour grid with work type down and complexity across, the difference in each cell and grey where withheld, with pooled against conditioned as two neutral gauges, one colour because it is a comparison between two ways of computing the same difference and not a verdict. Complexity is proxied by files changed in three bands, and the tooltip says nothing measures it directly. Inside a stratum output is lines delivered per person-day rather than commits: within a single work-type and complexity cell most contributor-days hold exactly one commit, so both sides pin near 1 and the ratio measures the shape of the grid rather than the work, reading -20% however the data was shaped, which is what a metric that has stopped measuring looks like. On a fresh demo clone it reads +19% pooled and +25% conditioned. The cell table lists the largest cells first; ordering by distance from parity had put a 24-against-13 cell reading +829% at the top, the thinnest evidence on the page presented as the headline. Cycle time per stratum works on the issue grain, which is far thinner, and its tooltip says an empty chart means not enough issues, not no difference. The strongest addition is within-person: each contributor's own assisted output against their own unassisted output, which holds the person constant and removes the confounder the cohort comparison cannot touch, who chose to use the tool. Beside it a change-size histogram per cohort, because two cohorts can share a mean and differ entirely in shape, and pooled against conditioned recomputed weekly so the mix effect is visible as the gap between two lines.
- **An Investment Case dashboard where every dollar is a typed assumption multiplied by a measured quantity, and no figure is a saving.** Nothing in the lake knows what a seat costs, what an hour costs or how many hours were saved, so a return figure built from an assumed hours-saved is an assumption wearing a chart. The assumptions are text boxes at the top, paid seats, cost per seat, cost per developer hour, working hours per month, so a reader sees which numbers are theirs; everything else comes from what `dun` records. Seats: paid against active, utilisation, cost per active user, and spend on unused seats, the one saving on the page a reader can actually make. Cost per unit of output: licence spend over the range divided by assisted commits, assisted lines and assisted issues closed, with the spend and both counts shown on the same row so the arithmetic is on the page; a total built by multiplying the per-issue cost back by the issue count was asked for and declined, because it returns the spend figure exactly on every range. Break-even is the row that carries the argument: hours per seat per month, hours per active user (higher when seats sit idle, since the people who use it earn back the ones who do not), minutes per assisted commit, minutes per active user per working day. ROI is a sensitivity grid and one labelled hypothesis rather than a percentage, because the cost side is complete and the benefit side is not: `dun` measures lines, commits, issues and cycle time, never hours returned. The grid runs hours saved per developer per month from half an hour to eight with the value returned, licence spend and ROI for each, so the reader picks the row they believe, and the row where ROI crosses zero is the break-even figure. The hypothesis stat is titled with its condition, if the conditioned output difference from the Productivity page were entirely time returned, and shows the hours that would imply beside it, coloured amber rather than green because a hypothesis is not good news. Typed inputs are cast and every division guarded, so a non-number renders blank rather than wrong.
- **Token spend is priced per model from the providers' own pricing pages, and fails closed.** The page took one typed price per million tokens and applied it to every model, which is wrong the moment two are in use: Opus 4 is $15/$75 and Sonnet 4 is $3/$15, and on the demo data the correct figure is $1,130 against $335 from one box. `fetch-model-prices.py` reads the Anthropic and OpenAI pricing pages into `whodunit_model_prices`, keyed by the model string agents record in `whodunit_sessions.model`, and each session joins to its own model's row; the two price inputs are gone. A pricing page that changes shape parses to nothing, and nothing must not become zero, so if a provider parses thinner than a dated snapshot baked into the script the snapshot is written instead, and the dashboard's price-list table shows `fetched` or `baked <date>` beside each row. As of 2026-09-03 the Anthropic page fetches cleanly at 17 rows; OpenAI's table is rendered by JavaScript and shows as baked until that changes. A session whose model has no price row is listed as unpriced with the reason and excluded from the total: unpriced is unmeasured, not free. The row is labelled as meaningful only under per-token billing.
- **A Delivery Forecast dashboard: does the team deliver nX faster, and when does the backlog drain.** The multiple is per head: issues closed per person-week after adoption divided by the same before, with person-weeks summed from who committed each week, so a team that doubled in size does not read as twice as productive. Blank under 10 issues a side, and labelled a difference between two periods, not an effect. Backlog is opened minus closed, cumulative, with each week's net flow as bars, because a team can close a record number in a week the backlog still grows. Drain date under three rates, pre-adoption throughput, the last 8 weeks and the best recent 4, each dividing open issues by closing rate minus the recent opening rate, and saying "never at this rate" when issues arrive faster than that rate closes them; on the demo data two of the three never drain, which is the honest answer rather than the flattering one. A burn-up continues opened and closed as dashed lines at their recent rates for 26 weeks, and the default time range runs that far into the future so the projection is visible. Productivity per task, commits, lines, person-days and hours open per closed issue and tasks per person-day, is split by whether any linked commit was assisted and blank under 5 tasks a side. Per-team and per-person rows attribute closed work through the commits linked to each issue, because tracker assignees are mostly empty (52 of 564 issues); an issue with committers on two teams counts for both and the tooltip says so. The per-team drain table has to use assignees, since open work has no commits yet, and so carries an `(unassigned)` row that on real data is most of the backlog, the honest size of what cannot be forecast per team until the tracker assigns work. The per-person gauge is one colour on purpose: throughput per unit of effort, not a ranking. Team and contributor filters reach every panel attributed through commits; backlog and burn-up stay unfiltered because an open issue carries no person until the tracker assigns it. Issues are counted, not sized, and the closing text says so.
- **Seven dashboards rebuilt beside their originals, each keeping what only it showed and adding what nothing did.** The originals are untouched and the rebuilt views import beside them; their demo copies are parked in a TBD folder (see Changed). A leadership view (`whodunit-leadership`) beside the executive summary, on the same variables and the same underlying queries so the two agree on every number, draws adoption, acceptance and assisted rework as three coloured bands across the weeks so a bad week reads down a column and a trend along a row, grey rather than red before adoption because absence is not failure. A board-facing delivery view (`whodunit-board`) beside the DORA dashboard benchmarks the four DORA metrics against the State of DevOps 2023 bands with the band named under each figure, then shows each week by week with the assisted share behind it; before-and-after is used only where the data has a before, since deployment and pull-request history starts the same week adoption did, and a closing panel lists what the page does not claim, because a board dashboard without one is the vendor slide this project exists to replace. An adoption rollout view beside Adoption: a state timeline of who made an assisted commit each week so retention reads as runs of green, new against returning users per week, days from a person's first assisted commit to their fifth, a lapsed list of people still committing who have not used the tool in two weeks, and per repository the assisted share beside the share of commits made with no tool present at all, which is the cheapest adoption gain on the page because it needs an install rather than persuasion. Agent Activity Hours as a weekday-by-hour grid in the chosen timezone with after-hours and weekend shares, and a note that it cannot tell people working late from agents left running. The Productivity Funnel with every stage counting people, each a subset of the one before, so the conversion between adjacent stages is a real rate where the original's mixed units made the fall between two bars mean nothing, and a drop-off table naming who is stuck at which stage. Attribution with a histogram of the agent's share of lines per assisted commit, evidence strength by agent, and evidence by repository with a no-verdict column, never folded into unassisted. Cost with weekly list-price spend stacked by model and cost per thousand agent-written lines by model, since a dearer model can be cheaper per line if it needs fewer tokens.
- **A demo database built from a copy of the real lake, so the dashboards can be shown on data that has teams in it.** Demoing on one developer's data had already cost a live demo: single-contributor data produced misleading trends, and team ownership cannot be shown when there is one person and no teams. `seed-demo.py` clones `lake` into `lake_demo` (a `--single-transaction` dump, so no locks) and adds only the org chart around the real commits, sessions and hash intersections: 4 teams, 12 contributors, incidents, identity aliases and per-team MCP profiles, which is the honest version of the story and can be said out loud. Cloning rather than generating, because a synthetic dataset has to reproduce every relationship the panels rely on and getting one wrong is an empty panel discovered mid-demo. Every statement in the script is an UPDATE or INSERT that would rewrite the attribution of every commit in production, so it refuses outright when the target is `lake`. The copy also fixes what the real data cannot render: sessions whose timestamps were Go's zero time are anchored to real event times, token, model and autonomy columns are derived from each session's own tool calls so the Cost dashboard renders, and the last 30 days are reshaped from an install-date collapse into a rising 25% to 76% ramp. Three agents in a fixed mix, claude-code 80%, codex 12%, agy 8%, identical across commits, events and sessions; agy reports no tokens, timing, reasoning or model, and its rows are left NULL rather than filled, because that absence is the product's argument. Demo dashboards publish into their own Grafana folder with every uid suffixed `-demo`, because Grafana's uid namespace is global and importing under the repo's own uids moved the real dashboards into the demo folder, which happened once. `lake` is verified untouched after every run.
- **Every dashboard grain now records who did the work itself, rather than looking it up through a shared row.** `whodunit_commits`, `whodunit_events` and `whodunit_sessions` each carry a `contributor` column, populated on the write path. Previously all three resolved the one fact every per-person panel filters on through a join to `whodunit_repos`, a row that everyone syncing the same repository shares, so the filter was only as correct as whichever sync ran last. Session panels were a third of that surface: 24 of the 68 dashboard targets that reached contributor through the join were sessions. The column is nullable and an unknown contributor is written as NULL rather than an empty string, because an empty string asserts that a person with no name did the work. Rows synced before the column existed are deliberately not backfilled from `whodunit_repos`: backfilling through the join that caused the collision would write a confident wrong name onto history.
- A `teams` map in `~/.whodunit/config.json` and a `$team` dropdown on the five dashboards that carry a contributor filter, so a manager can read group-level adoption instead of a list of named individuals. The map is keyed by team rather than by person, because that is the shape somebody maintains by hand: a team gains a member far more often than a person changes team. Config wins over DevLake's own team tables outright, since those are populated by a connector nobody here controls and a value someone typed on purpose should not be overruled by one that arrived on a sync. Aliases resolve before the team lookup, so a person's second machine lands in the same team as their first instead of splitting across a team and `(unassigned)`. `(unassigned)` is always offered in the dropdown even when nobody is currently unassigned, because someone will commit from an unmapped address and a list built from current membership hides them the moment they appear. The two dashboards with no contributor filter get no team filter, which would have been a control that does nothing.
- **Identity aliases now reach the dashboards.** `dun identities` and the `identities` config map already merged the addresses one person commits from, but neither reached Grafana: selecting a contributor still dropped every commit that person made from a different address. Measured on the development install, 148 of 1,263 commits sat under a GitHub noreply address and the rest under the real one, one person, and filtering to either lost the other. A `whodunit_identities` table publishes the map and 51 contributor filters compare against `COALESCE(canonical, contributor)` through a LEFT JOIN. Chains are flattened before they are written rather than followed in SQL, so what the dashboard resolves cannot disagree with what `dun identities` prints. Resolution is read-time only: the literal committer email stays in every commit row and every commit object, so a wrong entry is corrected by editing one line rather than by re-syncing history. With no aliases configured all 51 targets return byte-identical results to the plain form, so the feature is inert until you configure one. Five panels resolve contributor inside a subquery a pattern rewrite cannot reach and keep the direct comparison; they are correct as they stand and are not alias-aware yet.
- **An existing install migrates itself to the new sidecar key, once, with a verified backup taken first.** The key change alone reached only fresh databases: `CREATE TABLE IF NOT EXISTS` silently does nothing to a table that already exists, so the collision was fixed for new installs and left in place for every install that actually had data. Schema versions are now recorded in `whodunit_schema` and each rebuild applies once, gated on that version. Changing a primary key is a create, copy, drop, rename, and once a developer's local journal has pruned its line hashes after a successful sync the sidecar holds rows that exist nowhere else, so a failure midway is permanent loss. The backup therefore gates the rebuild rather than accompanying it: it is taken and verified by row count before any destructive statement runs, and a backup that cannot be taken or verified stops the migration. This is the one place in whodunit that fails closed; everywhere else attribution degrades rather than blocking work, but that reasoning protects your workflow and here the thing at risk is your data. The version is recorded only after the rebuild succeeds, since recording it first would turn one failure into a permanent skip, and a database with no recorded version is treated as version 1 rather than as current, because it predates the version table and needs exactly the migration it is here to receive.
- `brew upgrade dun` now repairs git hooks itself instead of printing a caveat asking you to run `dun repos update`. The formula claimed Homebrew has no post-install hook; it does, and it runs on upgrade as well as install. This matters because hooks record the version that wrote them, so a change to the hook script's shape does not reach a repository just because the binary was upgraded. `dun` repairs a repository on the next command run there, but a repository nobody visits stays stale indefinitely, attributing less while looking like it works. A repository that has moved, or whose hooks directory is not writable, does not fail the upgrade: stale hooks are a better outcome than no new binary.

### Changed

- **Team Adoption and MCP & Tools were each built twice this release, and the first build of each is retired.** The rollout view built beside each original covers everything it showed and adds the rollout questions, and two dashboards under one name is the confusion this removes: one dashboard per question. The originals are deleted from the repository and from both Grafana folders; the rollout views keep `whodunit-teams-board` and `whodunit-mcp-board` so existing links survive, and take the plain titles now that they are the only ones.
- **The Delivery Forecast's top throughput row follows the team and contributor filters.** It counted every closed issue against every committer with no person on either side, so the filters could not reach it and a team selection changed nothing. It is now built on the same commit-linked attribution as the per-team row. The cost is stated in each tooltip: only issues with a linked commit are counted, so the org-level multiple reads lower than the raw figure on the board dashboard, 2.93× against 4.27× on the demo. That is the price of being able to say it per team.
- Demo copies of the beside-built dashboards import into a TBD folder, so the demo folder holds one dashboard per question; the repository and the real folder carry them unchanged, and moving a uid out of `PARKED` in the seed promotes it.
- **`whodunit_repos` is now keyed on `(repo_id, contributor)`, so two people syncing one repository no longer overwrite each other.** `repo_id` is the repository's root commit SHA, identical for everyone who clones it, so on a key of `repo_id` alone the upsert made a second person's sync silently replace the first person's row. The lost row was not the damage: every commit the first person had already synced was reattributed to the second through the join, with nothing failing and the dashboards rendering a confident wrong answer. The composite key costs 1,536 bytes against InnoDB's 3,072 limit, confirmed against MySQL 8 rather than computed, which removed the case for hashing the email into a surrogate. An existing install is migrated automatically on the next schema check: rows are preserved, and the pre-migration table is left behind as a timestamped backup rather than dropped. On a shared install, rows present at migration time belong to whoever wrote last, so correct per-contributor attribution begins from the migration forward and a figure spanning that boundary reflects when the fix landed.
- **Two Adoption panels now group by team rather than opening on a ranked list of named developers.** "By contributor" and "Committed work by contributor" both grouped by name, and the default is what most people ever see: it decides whether the tool reads as team insight or as per-developer monitoring, and a leadership dashboard that opens on developers ranked by AI adoption is the objection that ends adoption inside a company. Both are renamed to match what they now show. Individuals remain one selection away through the Contributor filter, because a team default must not mean individuals are unreachable. The grouping resolves aliases first, so someone's second machine lands in their own team rather than splitting into a team and `(unassigned)`, which would read as two people with one unaccounted for. With no teams configured everything lands in `(unassigned)`, a working table rather than an error. The other three panels the concern could have covered group by time or by branch, where contributor is a filter and not an axis, so they already show no names and are untouched.
- Panel titles and series labels say **AI-assisted** and **not AI-assisted**. The bare words "assisted", "AI-assisted", "not assisted" and "other" all appeared across fourteen panels on five dashboards, two of them on the same dashboard, with no definition anywhere on screen; the question was asked out loud in a demo. "Other" is worse than inconsistent, it is not a cohort anyone can act on: read off a screen in a client conversation, "Median cycle · other issues" invites the reader to supply their own meaning. Unit suffixes are kept, because two panels in one row showing commits and lines both said "assisted" and read as though they disagreed. Field overrides were renamed alongside the labels, since an override matches on the label and a renamed column with a stale override silently loses its unit, colour and width. The Matched commits tooltip now names all six states: it described its cohort as narrowed one way, by commit type, when it is narrowed two ways.
- The datasource dropdown is removed from every dashboard. Selecting a different database changed the dropdown and nothing else: panels kept querying the previous one, with no error anywhere. Reproduced rather than assumed, with the dropdown reading a second datasource pointing at an 11-commit fixture while every panel still showed the 1,075-commit lake. These dashboards are bound by Grafana's import-input mechanism, which substitutes the datasource uid into every panel at import and bakes it in, so a template variable can never override it and the dropdown was decoration over a fixed value. Pinning at import is the right behaviour for a tool that ships dashboards into someone else's Grafana, so the variable goes rather than the pinning. Switching database is a re-import, which is the operation that actually changes it: `./import-dashboards.sh --datasource <uid>`.

### Fixed

- **The scatter panels crashed on load.** Both rendered "Loading plugin panel..." forever. The xychart plugin runs a v1-to-v2 options migration whenever `pluginVersion` is absent, and that migration maps over `options.series`, which the panels did not carry; the crash was in the migration, not the query, since every query returned rows. The panels now carry a plugin version so the migration is skipped, and v2's explicit shape.
- **"Tools used, by agent" drew every distinct tool name.** The panel had no limit, so it drew one bar per tool, 145 on the real lake, as a single unreadable band of rotated labels, broken on real data and not only the demo. ## [0.4.0] - 2026-08-25

### Added

- **`dun replay` and a durable record of attributions that failed.** A determination that broke — an unreadable journal, a failed ingest — left nothing behind that a later run could act on. Failures now append to `~/.whodunit/log/replay.log`, which nothing rotates away, carrying the staged files and agent-line count a retry needs. `dun replay` lists what is outstanding; `--apply` re-runs each one against the journal as it stands now, which is the case worth retrying, since a transcript ingested after the commit was made carries hashes that were not available at the time. Commits keep their original trailers either way — git history is never rewritten — and a resolved failure is cancelled by appending, so the record of what went wrong survives being fixed.
- **`observed` now says what happened to the agent's text.** The second-largest attributed tier meant "the agent edited this file and its exact lines are not what got committed" and stopped there. Commits now carry `changed_by=human` when a person revised the output before committing, or `changed_by=agent` when a later turn replaced its own earlier lines. Absent where nothing recorded it — only Claude Code reports this, so on Codex and agy the key is permanently absent rather than pending, and the reason is never inferred from the mere absence of a line match.

- Commits from **GitHub Copilot and Cursor are now attributed**. Both write a trailer into the commit and leave no local transcript, so every commit from a team using them previously came back `undetermined` — correct, since there was no evidence, and useless. whodunit reads `Agent-Logs-Url`, `Co-authored-by: Copilot` and `Made-with: Cursor`, and grades them `declared`: the weakest rung the spec has, because a trailer is the author's own assertion verified by nothing. Two guards keep it honest — a trailer key must be followed by a colon, so a commit *about* Copilot is not a Copilot commit, and `Co-authored-by` must name the agent, because that trailer is written by people about people far more often than by tools about themselves. A transcript always wins: `observed` and `intersected` outrank `declared`, so an agent that records what it did is never displaced by one that merely says so.
- `dun identities` lists every git committer email across your instrumented repositories and flags the ones that look like the same person, printing the configuration that would merge them. It changes nothing: merging two identities is a claim about who somebody is, so the command hands you the lines and leaves the decision with you. One machine configured with a GitHub noreply address and another with a real one splits a single developer in two without ever saying so — on the install this was built against, 148 commits sat under a second address.
- A `identities` map in `~/.whodunit/config.json`, resolving a committer email onto the person who owns it. Resolution happens when a figure is read, so the literal address stays in the journal, the sidecar and every commit object, and a wrong entry is corrected by editing one line rather than by re-syncing history. An address with no entry is its own identity — absent never means merged.
- `dun status` reports when attribution began in a repository and how many older commits predate it. Coverage alone invites the wrong reading: 13 of 100 covered looks like 87 commits somebody typed by hand, when they are commits made before whodunit was installed there. AI use before that boundary is unknown, not absent.
- A `LICENSE` file, Apache-2.0, covering the collector and the trailer grammar alike. The Homebrew formula has been declaring `license "Apache-2.0"` since packaging began while the repository carried no licence at all, so the claim reached every installer with nothing behind it and the code was all-rights-reserved by default. That also contradicted the project's own description of the trailer as a standard "meant to outlive any one implementation of it" — nobody could legally write a second implementation of a grammar nobody may copy.
- The README documents upgrading, which it did not: the commands, that hooks repair themselves, and the `brew upgrade` message that reads as a bug.
- An [Upgrading](website/docs/getting-started/upgrading.md) page, covering the three things an install consists of and which of them need you to do anything. Only the binary does: hooks repair themselves on the next `dun` command in a repository, and the dashboards are one re-import. It also names the `brew upgrade` case that reads as a bug — "0.3.0 already installed" means Homebrew has no newer version *in its tap*, which is not the same as no newer version existing.

### Fixed

- Charts no longer report zero AI use for the period before whodunit was installed. Commits are recorded from `dun init`, but attribution starts only when an agent transcript first matches one; in between every commit is `undetermined`, which means *no evidence* and was being plotted as 0%. On the install this was found on, 26 of 41 points on the adoption chart were false zeros, and four repositories showed 0, 4, 26 and 76 days between first tracked and first attributed commit — so the boundary is per repository, not global. The series is now absent before it rather than zero. Volume metrics stay plotted across the boundary, because commit counts and cycle time are read from git and are as true before instrumentation as after. Three correlation panels carried the same defect through a shared query, feeding weeks of false zeros into the `r` and `n` figures published beside them.
- The README and the commands reference now describe baseline capture as it actually works. Both still said a baseline records "the last 90 days" and "cannot be recaptured afterwards" — true before v0.3.1, and wrong since: the window is named with `--since`/`--until`, a bare capture prints help rather than measuring the wrong period, and a baseline *can* be captured after hooks are installed, because it reads history git already has. What closes permanently is the availability of an untouched window, not the chance to capture one. A reader following the old text would have concluded the comparison was lost to them.
- A packaging token that has expired, been revoked, or lost access to one of the two repositories now fails the release workflow with a message naming the cause, instead of skipping the way a deliberately absent token does. The two are different situations and looked identical: no token is a choice a fork makes, while a dead token is a setup someone meant to work. A fine-grained PAT expires within a year by construction, so this failure arrives on a timer rather than hypothetically. Both repositories are probed, because access is granted per repository and a token can be valid for one and missing the other.
- Homebrew and Scoop are now published by the release workflow rather than by hand, so an upgrade is available the moment a release is. Both were manual because pushing to a second repository needs a token `GITHUB_TOKEN` cannot provide — a reasonable trade while releases were also manual, and a silent failure once they were not: v0.3.1 shipped and the tap stayed on 0.3.0, so `brew upgrade dun` correctly reported nothing to do while a newer release existed. The formula is now generated from the checksums the release actually published, by `scripts/brew-formula.sh`, the counterpart to the Scoop manifest generator that already worked this way. With no packaging token configured the job warns and skips, and the release still publishes.

## [0.3.1] - 2026-08-16

### Added

- `dun baseline capture` takes an explicit `--since` and `--until`, so you can name the period you were working without an agent and have the metrics computed from git history for exactly that range. The window is recorded on the snapshot and published to the datalake, because a panel comparing before against after has to name both windows, and a day count says how long a window was but not when it was.
- `dun baseline capture --force` replaces an existing snapshot, printing the capture date, window and commit count of the one it is about to destroy. A baseline is still immutable without it: refusing to overwrite protects the only record of a window that cannot be recaptured, but it equally blocked correcting a capture made with the wrong range, which previously had to be deleted by hand. A forced recapture is stored as a new baseline rather than replacing the old row, so what was actually compared stays on record.

### Changed

- **The trailer is now `v=2`, and `status=undetermined` has been replaced by four values that say why.** In v=1 that one word covered four unrelated situations — nobody used an agent, an agent was active but touched none of the staged files, the hooks predated the commit, or attribution itself failed — and a reader could not tell which. Three of those are fine and one is a bug. Commits now carry `unassisted` (the hooks were watching and saw no agent — a human wrote it), `unmatched`, `uninstrumented` or `degraded`. `unassisted` is the only positive claim among them and the only one that could be wrong in a flattering direction, so it is stamped only where the journal was genuinely read; absence of evidence is `uninstrumented`. Commits stamped under v=1 keep `undetermined` — their trailers cannot be rewritten — and the version field is how a reader knows which vocabulary a trailer holds.
- **Anything asking "was this attributed" must now name the statuses it means.** Two panels computed it as `status <> 'undetermined'`, which silently absorbs every status added afterwards: an `unassisted` commit stops being undetermined and starts counting as attributed, inflating coverage while rendering a perfectly plausible number. Every such query now lists the unattributed statuses explicitly, and a guard fails the build on any panel that negates a single status.

- `dun baseline capture` now prints help instead of capturing when no window is given. It previously defaulted to the last 90 days ending today, which stops being a pre-adoption window the moment hooks are installed — so the no-argument path silently produced the one baseline nobody wants, with AI-assisted work recorded as the *before*. `--days 90` still does exactly what it did; it is now a deliberate choice rather than something you fall into.

## [0.3.0] - 2026-08-15

### Added

- The trailer now carries a format version, `v=1`, written first so it is read before the values it qualifies. It exists because `ratio=0.62` is well-formed under any definition of ratio: change the rule and every trailer already written silently means something else, with no error to notice. Trailers live in commit messages, so that ambiguity would be permanent — a migration can rewrite a column, nothing can rewrite pushed history. A trailer with no `v` is version 1 permanently, since that is every trailer written before the key existed. The version is bumped only when the *meaning* of a value changes, never when a key is added.
- The trailer records which model produced the work, where the agent reports one. Taken from the most recent relevant session entry rather than the first — a commit can contain edits from more than one model, and the turn that finished the work is the one worth attributing. Omitted rather than guessed when no entry recorded one.
- `dun sync` publishes the pre-adoption baseline, so the dashboards have a genuine before to compare against rather than inferring one from early history.
- `dun` now says when a newer release exists, once a day, on bare `dun` only — not on every command, and never from a git hook. The commit path makes no network request at all: a version check that can hang a commit is worse than an out-of-date binary. It stays silent when there is nothing to report, when the request fails or times out, and when you are running a build from source. Turn it off with `dun config set version_check off`, or `DUN_NO_VERSION_CHECK` / `DO_NOT_TRACK` in the environment.
- `scoop install dun` on Windows, from a bucket at [navjyotnishant/scoop-bucket](https://github.com/navjyotnishant/scoop-bucket) — the counterpart to the Homebrew tap. This closes a gap that was worse than an inconvenience: the archive had to be renamed and put on `PATH` by hand, neither step was documented, and the git hook resolves `dun` by name — so a Windows user who unzipped and ran `dun init` got every commit stamped `undetermined`, silently, which reads downstream as "no AI was used". The plain archive remains supported for anyone whose policy forbids package managers, and the README now documents all three routes.
- The dashboards import into a **Whodunit** folder rather than scattering across Grafana's root, and the import script fails when a dashboard in the repository is missing from its list — that list was hand-maintained, and the cost dashboard had been absent from it since the day it was written.
- A seventh Grafana dashboard, **Cost & Efficiency** (`whodunit-cost.json`): token use per model, cache read ratio and write payback with the 1.25x break-even drawn, agent-written lines per branch, autonomy granted, session duration, MCP calls per server, and the share of edits a human changed before committing. Every panel that an agent cannot fill says so rather than rendering zero.
- Compaction counts per session, and a dashboard panel for the compact rate. A long session costs more even when cached, because the whole context is re-sent every turn, and compacting is the one thing a person can do about it — measured here, 92% of turns ran above 150k context while 8% of sessions ever compacted. Read from Claude Code's `compact_boundary` records and Codex's `context_compacted`; Antigravity has no equivalent and is excluded from the denominator rather than counted as never compacting.
- Token counts, model, reasoning effort and permission mode are now read from both Claude Code and Codex sessions. Claude Code reports usage on every assistant turn and the totals are summed; Codex reports a running total per session, so the last one wins — summing those instead would overcount by 3,090x on a real transcript. Fields an agent does not report stay absent rather than becoming zero: Claude Code records no timing and does not separate reasoning tokens, Codex never reports cache writes, and agy reports none of it. A zero on a cost panel reads as "this agent is free".
- Every recorded edit and tool call now carries the model that produced it, the branch it landed on, the MCP server it went through, and — for Claude Code — whether a human edited the agent's output before it was committed. What an agent cannot report stays absent rather than becoming a value: agy records no branch (the branch-like strings in its store are a tracker's *suggested* branch inside an MCP response, not the checked-out one), and only Claude Code has the human-edited signal.
- `dun init` now says whether the hooks will still find `dun` tomorrow. The hook script resolves the binary from PATH at run time and falls back to the absolute path it was installed from, so a binary that is not on PATH works — until that file moves or is deleted, after which every commit is stamped undetermined with nothing announcing it. init now warns in that case, and separately when a *different* `dun` is first on PATH, since the hooks will run that one rather than the binary used to install them. Silent when the install is correct, and never fatal: a report, not a gate.

### Fixed

- Selecting a contributor emptied most panels on five dashboards. Grafana's MySQL datasource quotes a *selected* value but passes the all-value through verbatim, so no single spelling of a bare `$contributor` satisfies both cases: quoted, a real selection renders as `''email''` and the query fails; unquoted, `__all__` parses as a column name. Every panel now uses `${contributor:raw}`, which takes Grafana's quoting out of the picture entirely. A regression check rejects any bare `$contributor`, because a dashboard that renders on "All" is no evidence — "All" stayed green through both broken states.
- Repositories instrumented before a hook existed never got it. `pre-push` was added after some repositories were already set up, so those simply never synced, silently, with nothing to indicate anything was missing. Hooks now record the version that wrote them, are repaired automatically on the next `dun` command in that repository, and appear as stale in `dun status`'s cross-repo listing — the one view that reaches a repository nobody has visited in months. An existing non-whodunit hook is still chained rather than replaced.
- Codex sessions entirely outside an `--since` window were written as empty rows. The session id is read from the rollout's header before the cutoff is applied, so `dun ingest --since` over a recent window wrote one row per historical rollout — every counter zero, and a zero timestamp. Measured on a real repository: 74 sessions written, all empty, and each one then counted in the denominator of any per-session average.
- Claude Code assistant messages were overcounted by roughly 1.93x. One assistant message is written as several transcript records — one per content block — and each was counted separately, while Codex counted messages. The same `agent_messages` column therefore meant different things depending on which agent filled it, so any cross-agent comparison of engagement was wrong with nothing on the dashboard revealing it. Measured on the largest transcript on this machine: 12,029 records for 6,687 distinct messages.
- Codex MCP calls were undercounted by 44%. Codex tags an MCP call one of two ways — a prefixed name (`mcp__linear__save_comment`) or a bare name with the server in a separate `namespace` field — and only the first was counted; the `namespace` field was not read at all. Measured on one machine, 311 calls used the counted form and 243 used the ignored one. MCP tool names are now qualified as `server__tool`, so a server's `save_comment` no longer merges with a local tool of the same name. A namespace alone does not imply MCP: Codex also uses it for built-ins such as `multi_agent_v1`, which are correctly not counted.
- Antigravity (`agy`) acceptance rate was structurally unmeasurable. Every entry was written with outcome `unknown`, and the adapter's own comment stated that agy records no rejection signal — it does. `steps.status` is `NOT NULL`, indexed, and populated on every row. The eight non-success rows on this machine resolve into three distinct meanings rather than one: six carry `error_details` beginning "Permission denied" (a human declining, which is exactly what an acceptance rate is measured against), one "context cancelled", one nothing at all. An unrecognised status still maps to `unknown` rather than being folded into `failed`, because a status this code has not seen is a gap in what we know, not evidence of an error.

### Security

- Updated to Go 1.26.6, which fixes four vulnerabilities reachable from this code: GO-2026-6218 (`net/url`), GO-2026-6090 (`crypto/tls`), GO-2026-5972 (`encoding/asn1`) and GO-2026-5026 (`net/http`).
- Secret scanning runs in CI rather than only when someone remembers, over full history — the case that matters is a credential committed and later removed, which is gone from the tree and permanent in history.
- Baseline snapshots are written owner-only. They were `0644` while the directory around them was `0700`, so they were never actually exposed, but a file protected only by its parent stays protected only until it is copied elsewhere.

### Changed

- `dun report` reports **measured tokens per model** instead of a dollar figure derived from `monthly_spend`. That figure was a hand-typed subscription cost divided evenly over every agent-written line — an allocation dressed as a measurement, giving the same unit cost whether the agent ran once or a thousand times, and unable to answer per-model or per-branch. `monthly_spend` is deprecated: an existing config still parses, the value is ignored, and `dun config set` no longer offers it.
- The report shows cache efficiency per model, with the break-even marked. A cache write costs about 1.25x base and a read 0.1x, so a write needs roughly 1.25 reads to pay for itself — anything below that cost more than it saved, which a read-ratio alone hides. Cache writes count as uncached in the read ratio, because a write arrives uncached and is billed above base rate; omitting them turns a real 48% into a flattering 99%.
- The DORA dashboard's "Cost per 1,000 attributed lines" panel now reports **output tokens** per thousand lines instead of dollars. Its old figure came from a dashboard textbox defaulting to `$200` — a placeholder that was nobody's actual bill, divided evenly over every line. The textbox variable is gone.
- **Tokens, never currency.** Under a subscription the marginal cost of a token is zero, so multiplying by an API rate would report money nobody spent, and nothing in a transcript says which billing model a user is on. Anyone who needs a figure has their own contract and can multiply correctly.
- `make check` is now the single entrypoint for every gate — formatting, vet, tests, race detector, performance budgets, benchmark smoke-check, and the dashboard export check. CI calls these targets rather than keeping its own copy of each command, so the checks a developer runs and the checks CI runs cannot drift apart.
- Performance budgets extended from 3 gates to 13, covering both adapters that were previously unguarded. They assert and fail rather than printing a number, and scaling tests take the best of five runs on each side — a single timing on a shared runner is mostly noise.
- A test that asserts on elapsed time but is not selected by `make perf` now fails the build. The performance gate selects tests by name, so a badly-named timing test does not report as skipped, it simply never runs — which had already happened to two new tests before this check was added.

## [0.2.0] - 2026-08-14

### Added

- `dun verify` — one command that checks whether attribution is actually working: install, agents, hooks, journal, sync, and every registered repository, each finding paired with the command that fixes it. Output is grouped into sections with status icons, and the exit code is non-zero only for genuine breakage, so it can gate CI without failing a deliberate local-only setup.
- `dun sync` publishes attribution data to a shared DevLake database, with `dun config datalake` walking through host, database, user and credentials and testing the connection before saving. Publishing then happens automatically on push; the push hook never blocks a push and retries on the next one.
- `dun status` now works outside a git repository, printing a one-line summary of every instrumented repository, and takes `--repo <path|id>` to report on a specific repository from anywhere.
- `dun journal show` and `dun journal purge` take `--repo <path|id>` to inspect or clear another repository's data; purge names the repository before deleting.
- `dun delta` compares velocity and revert rate two ways — assisted vs. undetermined commits in the same window, and a baseline window vs. a recent one — flagging thin data, mismatched windows, and a missing baseline rather than printing a number that looks solid.
- `dun baseline capture` records a dated, immutable pre-adoption snapshot (commit volume, median diff size, revert rate, cadence, purpose mix) so a later before/after comparison has something to compare against.
- `dun init --repo` instruments a repository without changing directory, and a registry records what was instrumented: `dun repos list`, `dun repos candidates` (repositories with agent activity but no hooks), and `dun repos remove`.
- `dun update` upgrades the binary and rewrites hooks everywhere in one step; `dun repos update` rewrites hooks in every registered repository, preserving hooks whodunit did not write. Hooks now record the version that wrote them, so `dun verify` can report stale ones.
- Codex CLI and Antigravity CLI (`agy`) adapters, both reaching `intersected` confidence, alongside Claude Code.
- Transcript locations are configurable per agent via `dun config set agent.<name>.path` or `WHODUNIT_<AGENT>_PATH`, and `dun init` reports which agents it found while you are still watching.
- `dun report` gains inline SVG charts, journal-derived data (acceptance outcomes, per-tool and per-file activity, session engagement), and three presets — `exec`, `adoption`, `detail`. The report stays a single self-contained file with no external requests.
- Commits are classified by purpose (feature, fix, test, docs…) from Conventional Commits type, path heuristics and diff shape, and shown in the report as a distribution plus a commit-by-commit table.
- The DevLake datalake installs from two curl-pipeable scripts — `setup-datalake.sh` brings up the stack and creates the Grafana datasource, `import-dashboards.sh` imports the dashboards into any Grafana. DevLake's compose file is no longer vendored, only fetched from the upstream release asset. DevLake's own Grafana never creates its datasource — its entrypoint authenticates with a password its compose file never sets, so every attempt returns 401 — which is why the setup script creates it.
- `dun config` with no subcommand lists every setting, its value, and whether that value was set or defaulted, because a default and a deliberate choice read identically as a bare number. `dun config set` accepts `monthly_spend`, `backup_days` and `retention_days` alongside agent paths; all three were previously config-file-only, and the report advised a command that rejected the key. The accepted settings, the "unknown setting" message and the help text now read from one table, so they cannot drift apart again.
- The journal keeps daily rotating backups: a compressed copy taken on push, at most once a day, seven generations retained, written before pruning so the week of history predates whatever retention removes. The live database is never touched, and pruning runs only after a successful sync, so anything removed already exists in a second place.
- The hook log keeps five rotated generations of a megabyte each rather than one, holding months of history — long enough to answer "when did this start failing", which is the question the log exists for. `dun ingest` and `dun sync` now record their outcomes and failures there: an unopenable target, an unreachable one, a failed schema check, a failed write. Previously they printed to the terminal and left nothing behind, and `dun ingest` passed an empty error callback, so a transcript that could not be parsed was discarded silently by the code that would have reported it. The sync target is redacted before it reaches the log.
- Bare `dun` opens with a wordmark, the running version, and the full command list. The version is load-bearing rather than decorative: hook staleness is computed from it. The command list is derived from the command tree instead of a hand-maintained array, which had drifted to eight entries while `--help` showed eighteen, leaving `baseline`, `check`, `config`, `daemon`, `delta`, `ingest`, `update` and `version` invisible to anyone who never thought to ask for help.
- Grafana dashboards for the synced data — adoption, executive summary, and a coverage overview — including an export variant any Grafana can import, shipped as a tarball on each release.
- Bare `dun` prints a welcome screen explaining what the tool is, whether the current repository is instrumented, and the next command to run; output across commands is color-coded, honoring `NO_COLOR`, non-TTY output, `TERM=dumb`, and CI.
- Confidence levels explain themselves wherever they appear — `dun status`, the cross-repo listing, and the HTML report — with each method's position on the ladder stated (`intersected` strongest, `observed` weaker because the agent's text was changed before committing).
- Tool calls are classified as accepted, rejected, failed, or unknown, and acceptance rates always display next to the denominator they came from.

### Changed

- The commit hook looks back 30 days rather than 7. Seven covered a working week and lost anything that sat over a holiday or on a long-running branch, which is the work most likely to be agent-heavy; the wider window costs about 26ms per commit against a two-second budget. Retention is derived from that window rather than being a second 30 typed in a package that cannot import the first, because pruning inside the window the hook queries deletes evidence a commit was about to match — silently turning an `intersected` commit into an `observed` one. A `retention_days` below the lookback is refused by `dun config set` and clamped on read, so a value written before the minimum existed cannot route around the guarantee.
- `dun status` reports the real unsynced backlog — what has been recorded since the target last heard from this repository — rather than counting every journal entry ever recorded. A repository that had just published still claimed 2,726 events outstanding, which does not merely overstate the number: it says publishing accomplished nothing. What a sync transmits is reported separately, because a sync genuinely does retransmit the full history each time. The remote lookup is a single indexed read, and the cross-repo view answers for every repository in one query rather than one connection and one two-second timeout each.
- `dun sync` reports progress. It was silent between announcing the payload and reporting the result, which on 16,890 rows reads as a hang; it now names each network step and draws a progress bar through the write, to a terminal only, since a carriage-return redraw into a CI log produces thousands of lines.
- The local-only warning argues from correlation rather than data loss. The journal is regenerable from the agents' own transcripts, so "you will lose your data" overstates the case; what publishing buys is joining attribution to what happened next. What genuinely does not come back is a pre-adoption baseline and any commit whose agent transcript has since been pruned, and the message names those two rather than making a blanket claim.
- Status glyphs are text rather than emoji. Emoji carry their colour from the font, so a checkmark stayed green under `NO_COLOR` — the one case where output is meant to be plain — and rendered double-width, misaligning every column after the marker.
- **Breaking:** the `session` trailer value is now a repo-scoped hash rather than the agent's raw session id, which on Claude Code doubled as the transcript filename. Existing commits keep their original value; new commits are no longer a pointer into local transcript files and cannot be correlated across repositories.
- **Breaking:** the journal moved from one SQLite file per repository under `.git/dun/` to a single database under `~/.whodunit`, keyed by repository root-commit SHA. Baseline snapshots moved to `~/.whodunit/baselines/` so they survive a fresh clone or `git clean -xfd`.
- `~/.whodunit` separates settings (`config.json`) from regenerable data (`data/journal.db`) and non-regenerable baselines.
- `ratio` is a real measurement instead of a hardcoded `1.00` — the agent's deduplicated share of a commit over total changed lines. It is omitted rather than reported as `0.00` when there is no line-level evidence, and shares below 0.005 are omitted rather than rounded to zero.
- Attribution matches line by line, file-scoped, instead of whole tool outputs against whole diff hunks, so an agent's write still matches on the lines a developer kept. Only hashes are stored, never the lines themselves.
- The commit hook writes the journal itself, so a normal install reaches `intersected` without anyone remembering to run `dun ingest`.
- Repository identity, contributor email (from `git config user.email`, captured at `dun init`) and per-repository metadata are recorded once per repository rather than on every row, and `dun journal purge` removes them too.
- `dun report` writes to the system temp directory by default and prints an absolute `file://` URL.
- Repeat `dun ingest` runs are roughly 7× cheaper on unchanged transcripts, and the commit hook stays well inside a 2-second budget.
- DevLake dashboards are imported rather than mounted, so the bundled compose file stays stock and dashboards remain editable in Grafana.

### Fixed

- Attribution silently produced nothing on Windows. Four independent causes, each sufficient on its own: the directory-name encoding kept the drive colon and produced a name Windows refuses to create; the session directory came from an unresolved path, so the slug named a directory that exists nowhere and no transcript was ever found; line hashes included the raw path, so the staged half (`C:\repo\main.go`, from git) and the recorded half (`C:/repo/main.go`, from agents that are Node programs) never agreed; and staged files were matched against journal entries by exact string, so no key ever matched. Every one failed the same way — no error, no sessions found, every commit stamped `undetermined`, which reads as "no AI was used" rather than "the two halves spelled the path differently". Paths are now resolved once per file through a single implementation, and matching tolerates a volume prefix on one side while keeping `C:/repo` and `D:/repo` distinct: folding aggressively enough to merge them would manufacture attribution that never happened. The sync password was also unprotected there — `os.Chmod` only toggles the read-only attribute and `os.Stat` synthesises the mode it returns, so writing `0600` granted nothing and checking for it read back a number the runtime invented. The key and ciphertext now carry a protected owner-only ACL, verified by reading the descriptor back.
- A commit made while the daemon was ingesting lost its attribution. One journal file per machine is written by the commit hook on every commit, the daemon every five seconds, and `dun ingest` by hand, across every repository at once — and the database was opened with no `busy_timeout` under SQLite's default rollback journal, so a second writer failed immediately with `SQLITE_BUSY`. Every caller treats a journal error as "record nothing and carry on", which is correct and made the cost invisible: the commit was stamped `undetermined`. Reproduced at 3 failures in 200 concurrent writes before the fix, none after, with WAL, a five-second busy timeout, and a retry around schema creation that `busy_timeout` cannot cover because there is no database file to wait on yet.
- Backups were disabled on every fresh install. The `backup_days` default was applied after the "no config file" early return, so a machine with no `config.json` loaded zero, which `journal.Backup` reads as "explicitly disabled" — it silently took nothing while the prune beside it still deleted line hashes. The ordering that makes pruning safe, copy first then delete, was absent on exactly the machines most likely to need it: every one, on day one. That also exposed the second half: `backup_days` carried `omitempty`, so `dun config set backup_days 0` wrote no key and read back as the default, meaning the documented way to disable backups quietly re-enabled them.
- `dun config` printed the sync password. The redaction helper returned the raw DSN when the URL failed to parse — precisely when someone is looking at the output, since an unparseable DSN is what they are trying to diagnose — and never touched a password passed as a query parameter. Three of five cases leaked.
- A malformed `config.json` was swallowed. Falling back to the built-in defaults is correct, since a broken file must not silence an agent outright, but nothing reported it on the path that matters: the commit hook never loads the config directly. A stray comma discarded every configured agent path, every commit was stamped `undetermined`, and the only signal was attribution quietly stopping. The hook now logs the parse failure.
- The repositories registry could be read mid-write and fail to parse, taking every cross-repo command down with it — 7 of 100 reads with one concurrent writer, because the write truncated the file before rewriting it. That file is not regenerable: it is the list of repositories someone chose to instrument, and rebuilding it means re-running `dun init` in each one, if they realise that is what happened. It is now written to a temporary file and renamed over the target. On Windows, where a rename is refused while another process holds the file open for reading — exactly the case this protects — the rename retries for about a second rather than failing `dun init` because someone ran `dun status` at the same moment.
- Three user-facing messages said "the last 7 days" long after the window became 30. The behaviour was right and the explanation was wrong, which is worse than either alone: someone debugging a missing trailer reads that their three-week-old session is out of window, believes it, and stops looking. All three derive from the lookback constant now, and a test fails if a literal creeps back.
- Storing the sync password failed with "cannot determine a machine identifier" on machines that plainly have one. The machine id shelled out to a bare command name, which a hook running with a minimal `PATH` need not find; it tries the absolute path first now.
- A fresh DevLake install ended up with a running stack and an empty Grafana. The setup script polled Grafana's health endpoint, which returns 200 well before the API accepts an authenticated write, and DevLake's entrypoint deletes and recreates any datasource named `mysql` seconds after Grafana starts, removing one that landed first. Re-importing dashboards also duplicated them — the export blanked each dashboard's uid, so Grafana minted a random one per import and `overwrite` matched nothing, turning six dashboards into twelve on one re-run. The exports additionally carried the author's own team id, timezone and spend as pinned values, which made valid SQL return nothing on anyone else's machine, in the way that reads as "no data" rather than "not configured".
- A test-only panic path shipped in every release binary: `dun hook panic-probe` triggered a deliberate panic, recovered and harmless, but a test fixture has no business in a shipped binary.
- Commands run outside a git repository say what is wrong and how to proceed (`use --repo <path>`) instead of surfacing `exit status 128`.
- `dun verify` no longer reports per-repository agent session counts when run outside a repository, and distinguishes an agent that is not installed from one whose configured path is wrong.
- `dun delta` counted every assisted commit as undetermined when the trailer sat at the end of a multi-line commit body.
- Release builds report their version instead of reporting none.
- Journal directories are created `0700` and the database `0600`, and existing over-permissive files are repaired on open — the journal records which files were edited and when, and was previously world-readable.
- The schema applies cleanly to MySQL as well as SQLite, fixing three portability bugs (a `TEXT` default, index creation syntax, and an over-long primary key) that made a live deployment impossible.
- `dun check` in CI no longer fails on GitHub's synthetic merge commit, which was never authored through the hooks.

### Security

- The sync password is encrypted at rest with AES-256-GCM under a machine-derived key, replacing environment-variable-only storage that pushed users toward a plaintext credential in `~/.zshrc`. It protects the credential if the file leaves the machine — a backup, a synced dotfiles repo, a copied home directory — but not against a process already running as your user. `dun verify` reports where the password lives and fails when either file is readable by others.
